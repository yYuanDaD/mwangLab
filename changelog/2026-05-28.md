### 7. proteomics 工具 #3:`preprocess_proteomics_matrix`

**`@tool` 签名:** `preprocess_proteomics_matrix(quant_path, labeling, output_dir, missing_threshold=0.5, minprob_shift=1.8, minprob_width=0.3)`

**验证过程顺手发现 + 修了 2 个 PRIDE 真实世界 bug:**

#### 8.1 LFQ regex 太严(撞 PXD028408)
- 提交者写 `"LFQintensities"` 一个词(无空格)
- 原 `\blfq\b` 末尾要求 word boundary,被 `i` 字母堵了
- **修法:** `\blfq[a-z]*\b` —— 复合词形态在 proteomics 几乎总是 LFQ 相关

#### 8.2 `quantificationMethods` populated-but-unrecognized 落入 "unknown"(撞 PXD025560)
- PXD025560 的 `quantificationMethods=["TIC"]` —— TIC 是 LFQ 的 normalization 变种,但我的 regex 不识别
- PRIDE 词表的非-reagent 项几乎都是 LFQ 变种(TIC / iBAQ / MaxLFQ / Spectral counting / XIC)
- **修法:** rung 1 如果 `quantificationMethods` 有值但没匹配到任何 labeled reagent,默认 `label_free` 并在 reasoning 加 "(unrecognized term)"

**3 个真实 fail mode 都 fail-loud 正确处理:**
- PXD028408 = identification-only mzTab(只有 PSM/peptide counts,无 abundance 列)→ parser 现在精确报 `mzTab-type='Identification'` 而不是"no per-sample intensity"
- PXD000001 = 2012 老 PRIDE auto-mzTab(abundance 几乎全字面 "null")→ 报 100% missing
- PXD019643 = RAW only → 报 NO QUANT MATRIX

### 9. v1 polish:protein ID 检测 + score 列排除

PXD025560 spot-check 暴露 2 个数据卫生问题:

#### 9.1 Score 列污染样本检测
- `PG.Pvalue` / `PG.Qvalue` / `PG.Cscore` 都是数值,被算成假"样本"
- 真实 210 cols = 1 P-val(被错当 index) + 2 score + 1 ProteinGroups + 1 ProteinDescriptions + **208 真样本**
- 加 `_is_score_or_stat_column`(11 个 regex):`[qpe][._\s-]?value` / `pvalue|qvalue|evalue` / `c[._\s-]?score` / `score` / `coverage` / `(num|n)[._\s-](psm|peptide|protein|spec|ms2)` / `ms[/_. -]ms[._]count` / `(unique|distinct|razor)[._]peptide` / `sequence[._]length` / `mol[._]weight|mw` / `pep`(单独)

#### 9.2 Excel index 选错
- `pd.read_excel(quant_path, index_col=0)` 盲拿第一列 → 选中 `PG.Pvalue`(score!)
- 真蛋白 ID 在第 4 列 `PG.ProteinGroups`(值是 gene symbols 如 `A1BG, A2M, AAK1`)
- 加 `_find_protein_id_column`(7 个 pattern,优先序):`protein.?group` / `protein.?accession` / `majority.?protein` / `protein.?id` / `^accession$` / `^uniprot` / `^entry$`,fallback col 0

**PXD025560 重跑对照:**

| | Before polish | After polish |
|---|---|---|
| shape | 3318×**210** | 3286×**208** ✓ |
| index 列 | `PG.Pvalue`(score) | `PG.ProteinGroups`(真 ID)✓ |
| index 首值 | (数值) | `A1BG, A2M, AAK1`(gene symbols)✓ |
| score 列泄露 | 3 个 | 0 ✓ |

合成回归测试 `test_id_and_score_filtering`(Spectronaut-like Excel:3 score + ID + description + 4 samples)7 个 sub-check 全过。

### 10. `_classify_matrix` 误判混合 FPKM+diffexp 文件(GSE317978 副发现 bug 修复)

GSE317978 的 `core_table3.csv.gz` 混 6 个正 `fpkm_Sample*` + 6 个 `diffexp_*_log2fc / pvalue / qvalue`(后者有负值)。旧 `_classify_matrix` 看到负值就判 `log_transformed` → 跳 log2 transform → limma 跑在 raw FPKM(max=666117)→ 9906/17043 ≈ 58% DEG,生物上不可信。

**修法(`tools/batch_tools.py`):**
- 加 `_is_derived_stat_column` regex(`diffexp` / `log2fc` / `log2fold` / `lfc` / p/q values / `padj` / `fdr` / t/f/z-stats / `score` / `mean|median|variance` / `std|sd|sem|stderr`)
- `_classify_matrix` 在 sign/magnitude 检查之前过滤掉这些列
- `_align_metadata_to_expression` 复用同 filter(decisions.json 新加 `n_sample_cols_after_stat_filter` 字段)
- **顺带放宽 FPKM 阈值:** 旧 `has_dec and max < 1000 → fpkm_or_tpm` 太严(真实 FPKM 经常 >10k housekeeping genes),改成 `has_dec and max ≥ 30 → fpkm_or_tpm` + `has_dec and max < 30 → log_transformed`(log2(CPM+1) cap ~25)

**GSE317978 验证 before/after:**

| | OLD | NEW |
|---|---|---|
| matrix_type | `log_transformed`(误判)| `fpkm_or_tpm` ✓ |
| log2_transform step | 跳过 | **applied** |
| limma 输入 max | 47617(raw FPKM 当 log!)| **19.35**(真 log2 scale)|
| n_deg(padj<.05+\|logFC\|>1) | 不可信 | **305 / 17043 = 1.8%**(合理)|

### 11. GSE283691 重跑链式发现 `_find_expression_file` artifact pollution(third bug)

用户说"重跑"验证 GSE283691 double-log fix。第一次重跑结果竟然跟 OLD 一样(1 DEG / 9 GSEA)—— 反常,深查发现:

`_find_expression_file` 按文件大小排序候选 → pipeline 自己产出的 `<base>_log2.csv`(21.4MB)和更糟糕的 `<base>_log2_log2.csv`(21.5MB,来自我之前 bugfix run 的链式 log)比源文件(19.6MB)还大,被当成 "largest analyzable file" 选中。所以新 classifier 看到的是 **triple-logged 文件**(max=2.36),分类成 log_transformed → limma 直接跑 → 结果跟 OLD 一模一样。

**修法:** `_find_expression_file` 加文件名 artifact 过滤(`_log2.csv` / `_preprocessed.csv` / `_aligned.csv` 都跳过)。pipeline 自己的中间产物不会再 re-enter source data。

**清干净 + 第二次重跑(真实 before/after):**

| | 第一次 `limma_validation` | bugfix 那次(选错 log2 artifact)| **clean 重跑** |
|---|---|---|---|
| 选中文件 | source(误判 fpkm)| `_log2_log2.csv`(triple-logged)| source ✓ |
| limma 输入 max | 4.14(double-log)| 2.36(triple-log!)| **~17(原 log scale)**|
| DEG(padj<.05+\|logFC\|>1) | 1 | 1 | **0**(压缩 scale 下的假信号消失)|
| GSEA hits | 9 | 9 | **11**(broader dynamic range 多 2 个通路)|

OXPHOS / MYC TARGETS V1 仍是 top 2(NES=2.30 / 1.90,FDR q=1e-3)—— HFD-vs-SD 在 muscle 的经典 pathway 信号,scale 修对后 effect size 反而更大。
